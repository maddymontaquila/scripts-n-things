# Editorial voice guide

Use this as a standing profile for Maddy's release-blog voice, then refine it with live samples from the current repo and recent authored posts.

## What the voice should feel like
- upbeat, confident, and genuinely excited
- technical without sounding dry
- direct and conversational, like a teammate sharing the good stuff first
- opinionated enough to signal what matters most
- proud of progress without sounding self-congratulatory

## What to optimize for
- curation over completeness
- user value over internal implementation detail
- momentum over caution-heavy framing
- clear practical payoff over vague adjectives
- narrative flow over changelog order

## Common patterns to preserve
- lead with the release energy and why it matters now
- move quickly into the best highlights
- give concise context for why each item matters to app developers
- use links for deep detail instead of trying to retell every document
- close with a friendly invitation to try the release and share feedback

## What to avoid
- sounding apologetic or defensive
- burying the strongest feature in the middle of a long list
- describing the release as mostly prep work unless that framing is explicitly desired
- turning the post into a changelog dump
- generic AI phrasing like "we are thrilled to announce" unless it honestly fits the sentence

## Editorial heuristics
- if there are too many candidates, pick the few that best tell the release story
- if one feature is especially requested or strategically important, give it more room
- if the release has a theme, thread it through the intro and transitions
- if a line sounds polished but not personal, rewrite it to sound more like a developer talking plainly
- when in doubt, favor clarity and conviction over flourish
